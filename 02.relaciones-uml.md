# Relaciones entre clases y UML

## ¿Por qué importan las relaciones?

Hasta ahora cada clase ha vivido sola. En la realidad, los objetos colaboran entre sí: un vuelo tiene pasajeros, una biblioteca tiene libros, un hospital tiene pacientes y médicos. Las **relaciones entre clases** modelan exactamente eso.

Hay tres tipos fundamentales:

---

## 1. Asociación

**"Un objeto conoce a otro."**

Es la relación más general. Un objeto tiene una referencia a otro, pero ambos pueden existir de forma independiente. Ya la viste con `DepositoAgua`: el depósito principal conoce al secundario, pero si no estuvieran conectados, cada uno seguiría existiendo sin problema.

### Ejemplo en código

```java
// Un Médico atiende a un Paciente.
// Si el médico deja de existir, el paciente sigue existiendo.

public class Medico {
    private String nombre;
    private Paciente pacienteActual;  // referencia al objeto Paciente

    public void atender(Paciente p) {
        this.pacienteActual = p;
        System.out.println(nombre + " está atendiendo a " + p.getNombre());
    }
}
```

### En UML

```
┌───────────┐          ┌───────────┐
│   Medico  │ ────────>│  Paciente │
└───────────┘          └───────────┘
```
Línea simple con flecha abierta. La flecha indica quién "conoce" a quién.

---

## 2. Composición

**"Un objeto está formado por otros. Sin el todo, las partes no tienen sentido."**

La parte no puede existir sin el todo. Si el objeto principal se destruye, sus partes también. El ejemplo clásico: un `Vuelo` tiene `Asientos`. Un asiento sin vuelo no tiene sentido.

### Ejemplo en código

```java
// Un Vuelo está compuesto por Asientos.
// Si el vuelo se elimina, sus asientos desaparecen con él.

public class Asiento {
    private String codigo;   // ej: "12A"
    private boolean ocupado;
}

public class Vuelo {
    private String numero;
    // El vuelo crea sus propios asientos — no vienen de afuera
    private Asiento[] asientos;

    public Vuelo(String numero, int capacidad) {
        this.numero = numero;
        this.asientos = new Asiento[capacidad];  // el vuelo crea sus asientos
    }
}
```

### En UML

```
┌───────────┐ ◆────────>┌───────────┐
│   Vuelo   │           │  Asiento  │
└───────────┘           └───────────┘
```
Rombo **relleno** (◆) del lado del todo. El rombo indica que la parte vive dentro del todo.

---

## 3. Agregación

**"Un objeto contiene a otros, pero las partes pueden existir sin él."**

Es una composición más débil. El todo agrupa a las partes, pero si el todo desaparece, las partes siguen existiendo. Ejemplo: una `Biblioteca` tiene `Libros`. Si la biblioteca cierra, los libros siguen existiendo.

### Ejemplo en código

```java
// Una Biblioteca agrupa Libros.
// Los libros existen independientemente de la biblioteca.

public class Biblioteca {
    private String nombre;
    private Libro[] catalogo;  // los libros se crean fuera y se agregan

    public void agregarLibro(Libro libro) {
        // recibe un libro que ya existe — no lo crea
    }
}
```

### En UML

```
┌────────────┐ ◇────────>┌───────────┐
│ Biblioteca │           │   Libro   │
└────────────┘           └───────────┘
```
Rombo **vacío** (◇) del lado del todo. La diferencia con composición es solo el rombo: relleno vs vacío.

---

## Resumen de los tres tipos

| Relación | Símbolo UML | Dependencia | Ejemplo |
|---|---|---|---|
| Asociación | ────> | Ninguna — ambos independientes | Médico → Paciente |
| Composición | ◆────> | Fuerte — la parte no existe sin el todo | Vuelo → Asiento |
| Agregación | ◇────> | Débil — la parte puede existir sola | Biblioteca → Libro |

> **Truco para distinguirlas en un examen:** pregúntate "¿tiene sentido que la parte exista sin el todo?". Si no tiene sentido → composición. Si sí tiene sentido → agregación. Si no hay relación todo-parte sino solo conocimiento → asociación.

---

## Multiplicidad

En UML se puede indicar cuántos objetos participan en cada extremo de la relación:

| Notación | Significado |
|---|---|
| `1` | exactamente uno |
| `0..1` | cero o uno (opcional) |
| `*` | muchos (cero o más) |
| `1..*` | uno o más |

### Ejemplo

```
┌───────────┐ 1        * ┌───────────┐
│ Biblioteca│ ◇────────> │   Libro   │
└───────────┘            └───────────┘
```
Una biblioteca tiene muchos libros. Cada libro pertenece a una biblioteca.

## Cómo diagramar en draw.io

### Paso 1 — Abrir draw.io

Ve a [diagrams.net](https://diagrams.net) en el navegador. No requiere instalación ni cuenta.

### Paso 2 — Crear un nuevo diagrama

Haz clic en **Create New Diagram** → selecciona **Blank** → dale un nombre → **Create**.

### Paso 3 — Activar las formas UML

En el panel izquierdo, haz clic en **Search Shapes** y escribe `UML`. Aparecerá la sección de formas UML. También puedes ir a **More Shapes** (botón al fondo del panel) → activar la categoría **Software** que incluye UML.

### Paso 4 — Crear una clase

Arrastra la figura **Class** al lienzo. Verás tres compartimentos: nombre, atributos y métodos. Haz doble clic en cada sección para editar el texto.

```
┌──────────────┐
│    Libro     │  ← doble clic para editar nombre
├──────────────┤
│ titulo       │  ← atributos (uno por línea)
│ autor        │
├──────────────┤
│ prestar()    │  ← métodos (uno por línea)
│ devolver()   │
└──────────────┘
```

### Paso 5 — Crear la relación

Pasa el cursor sobre el borde de una clase hasta que aparezcan las flechas azules. Arrastra desde ahí hasta la otra clase. Luego haz clic derecho sobre la línea → **Edit Connection** para cambiar el tipo:

- **Association**: línea con flecha simple
- **Composition**: línea con rombo relleno
- **Aggregation**: línea con rombo vacío

También puedes añadir la multiplicidad haciendo doble clic sobre los extremos de la línea.

### Paso 6 — Exportar

Menú **File → Export as → PNG** (o SVG para mayor calidad). Listo para pegar en una presentación o documento.
